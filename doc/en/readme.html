Add-on Developer Updater

Version 2026.2.35. Add-on versions follow the current stable NVDA release family. This release supports NVDA 2025.3.3 and later and is tested through NVDA 2026.2.

This add-on checks official NVDA releases and safely monitors approved NVDA add-on development projects in configured folders and locally synchronized cloud storage.

Quick start

  1. Press NVDA+Alt+Shift+U to scan your normal development folders.
  2. Approve only maintained development projects in the discovery window.
  3. Assign the command named Review previously discovered NVDA add-on compatibility updates in NVDA's Input Gestures dialog.
  4. Run that command, select intended manifests with Space, and press Enter to review the exact changes.
  5. Review all changed source and documentation before using the GitHub publishing command.
  6. Press NVDA+Alt+Shift+S for the final Store-readiness check. Review and submit the official form yourself.

Commands

Press NVDA+Alt+Shift+U to start a manual check and save its results. If new projects are found, an accessible approval window opens after the scan; nothing is selected by default. Separate assignable commands review saved compatibility updates, undo the most recent group of discovered compatibility updates, review projects still awaiting approval, report complete update-check status, scan all accessible drives, and cancel a running scan.

The review window is modeless: it does not block NVDA's main event loop, and NVDA commands continue to work while the window is open. In its update list, press Space to check or uncheck an item, Control+A to select all, Enter to update the checked items, or Escape to close.

Manifest updates are announced but no longer open project folders automatically.

Press NVDA+Alt+Shift+D to open the modeless Set an older NVDA compatibility target window. Official NVDA Add-on Store versions are loaded on a worker thread, with the last successful response saved for offline fallback. Select add-ons first; the version list then offers only older targets valid for every selected manifest and never offers a target below any selected minimumNVDAVersion. Experimental targets are offered only when every selected manifest uses the beta or development update channel. Each entry states the add-on path, Git branch, current last-tested and minimum NVDA versions, and whether the manifest has uncommitted changes. Review compatibility changes opens a final confirmation naming every proposed change and warning about dirty manifests. Only lastTestedNVDAVersion changes; NVDA, source code, minimumNVDAVersion, and the add-on's own version remain untouched. This metadata change does not prove code compatibility. If source uses newer NVDA APIs, check out the appropriate older source branch instead. Every changed manifest is backed up and revalidated. Failed validation restores the original automatically.

The command named Undo the most recent compatibility target changes is available in NVDA's Input Gestures dialog. It restores the last group of compatibility manifests only while each manifest is byte-for-byte unchanged since the operation. Missing backups, changed manifests, and invalid restored files are reported without overwriting later work.

Press NVDA+Alt+G or NVDA+Alt+Shift+G to open an accessible checklist of approved development projects. Nothing is selected by default. Select the projects to inspect and publish with Space, use Control+A to select all, and press Enter to continue. The preflight then filters the selection to projects with changed files, unpushed commits, no GitHub remote, or a local version that differs from the newest GitHub Release. Changes can include Python code, manifests, documentation, translations, tests, or configuration. A modeless Yes/No confirmation reports changed-file and unpushed-commit counts and public repositories that will be created before anything is staged or pushed. Credential-like files cause the preflight to fail. During longer operations, NVDA announces each project's inspection, repository preparation, commit, push, package upload, and release completion, including its position in the selected list. After a successful source push, the add-on compares each local manifest version with the newest GitHub Release. Matching versions are skipped. Missing or different releases are listed with both versions in a separate Yes/No confirmation asking whether to publish the local versions. Git and GitHub commands run on worker threads and require an authenticated GitHub CLI installation.

Press NVDA+Alt+Shift+F to load the newest released .nvda-addon files owned by the GitHub account currently signed in through GitHub CLI. The network lookup runs on a worker thread. For each repository, the newest non-draft release containing an add-on package is presented in an accessible single-selection list with its release tag, asset filename, and public, private, archived, or prerelease status. Repositories without a downloadable add-on package are excluded. Choose Copy download URL or press Enter to place the selected asset's direct HTTPS download URL on the clipboard. The gesture can be changed in NVDA's Input Gestures dialog.

Press NVDA+Alt+Shift+I to select an owned NVDA add-on repository and open its GitHub Issues page. Repositories where Issues are disabled are identified and are not opened.

Press NVDA+Alt+Shift+T to select an owned NVDA add-on repository and choose an existing Markdown or YAML file directly inside .github/ISSUE_TEMPLATE. The accessible Form tab provides clearly explained template fields and, for GitHub YAML issue forms, a question list with controls for each question's type, ID, label, help text, placeholder, rendered language, default value, options, and required state. Every editable control has an explicit accessibility name, ensuring NVDA announces its purpose when focus moves to it. Every label explains where its value appears or what it changes on GitHub. Technical YAML types are spoken as Short answer, Long answer, Drop-down choice list, Checkbox list, and Information text. The editor defines Markdown as ordinary text with optional formatting symbols, gives examples for headings, bullets, and links, and makes clear that ordinary unformatted text is acceptable. Questions can be added, removed, or reordered before saving. A Raw Text tab supports advanced edits and files such as config.yml. Switching from raw text back to the form validates the YAML first. Form editing preserves unrecognized properties but may normalize YAML formatting and comments. Control+S or Save to GitHub opens a confirmation before any change is made. Delete Template has a separate warning and confirmation. Saving and deleting include the exact file revision that was loaded, so GitHub rejects a conflicting operation rather than overwriting or removing a newer remote edit. The editor also rejects invalid required metadata, duplicate or malformed question IDs, empty choices, empty files, files larger than 1 MB, nested paths, unsupported extensions, incomplete repository trees, and archived repositories.

When multiple local copies of one add-on exist, GitHub publishing shows only the copy with the newest add-on version. Numeric components are compared numerically, so version 1.10 is newer than 1.9. If versions match, the primary development folder is preferred.

A Codex work copy is hidden in favor of a primary development copy only when its add-on version is equal or older. A newer work copy remains eligible, ensuring its own GitHub remote and release history are inspected.

Repository discovery applies to every selected add-on. The updater uses the local origin remote first, then a GitHub repository URL in the manifest, then a matching repository in the signed-in GitHub account. It creates a new public repository only when none of those exists, and connects the local repository before pushing.

After GitHub inspection, NVDA announces each selected add-on's current GitHub Release and newest local version before asking whether to push anything. A repository with no release is announced as none. A new release targets the exact commit just pushed, even when the development branch differs from the repository's default branch.

During interactive GitHub operations, the updater progress window remains active and its focused status field is updated with every spoken publishing message. Focus moves from it only when the updater opens a confirmation or GitHub sign-in page, or when the operation finishes. Background scans remain non-activating.

If the newest local release is already published on GitHub, a focused information dialog says that the GitHub releases are current. Press OK to close it.

Existing GitHub Release assets are imported into the updater's submission metadata when their release version matches the newest local version. This allows the store-submission command to use releases created before the updater recorded them.

The store-submission gate verifies every add-on independently. Its release must use HTTPS on github.com, belong to the currently signed-in GitHub account, and contain a downloadable .nvda-addon asset from the same repository and matching release tag. The updater safely downloads the asset and verifies that its root manifest contains the expected add-on ID and local version; cosmetic package filenames may differ. The local working tree must have no changed files or unpushed commits. Ready and blocked add-ons are listed separately, with every blocked add-on's exact reasons. Only verified-ready forms can be opened.

Choosing No during GitHub sign-in, push, or release confirmation ends on a focused updater result dialog instead of returning directly to the previously active application.

When a progress window is replaced by a confirmation or result dialog, delayed progress cleanup restores focus to the replacement dialog. This prevents Windows from activating the application that was focused before publishing began.

If an add-on with the same manifest name exists both under the primary Documents\NVDA Add-on Development\Add-ons tree and a Documents\Codex work directory, the Codex work copy is persistently ignored. The GitHub command announces how many duplicate work copies were hidden, and visible projects are labeled by location. Same-name projects elsewhere are not removed automatically.

If GitHub CLI is not signed in from NVDA's process, the add-on offers a modeless Yes/No sign-in prompt with Yes focused by default. Pressing Enter starts GitHub's secure browser device flow, copies its one-time code to the clipboard, explicitly opens GitHub's device authorization page, and automatically retries the publishing preflight after authorization. The add-on never requests or stores a GitHub password or token.

Press NVDA+Alt+Shift+S to choose which approved add-ons to review for store submission. Nothing is selected by default. For each selected add-on, the updater checks the newest local copy, GitHub repository and exact-version release, the downloaded package manifest, current NVDA API-version requirements, HTTPS metadata, release channel, and every shipped text file for automated-authorship or generated-code disclosures. Legitimate references to a product the add-on supports, such as ChatGPT, are not treated as authorship disclosures. Any blocker is reported with the affected file and line when available, and no form is opened for that add-on. When all checks pass, the updater offers to open a prefilled official issue form for the user to review and submit personally. The updater never creates or comments on an addon-datastore issue; final review and submission are always performed by the user in the official form.

Store form titles and ready-list labels use each repository's current GitHub name. The manifest name remains the stable internal NVDA add-on ID used to verify package identity, so rebranding a repository does not break upgrades for existing users.

Only when preparing the official store form, the publisher field is filled as Justin Coffin. This does not rewrite an add-on manifest's author field, source files, Git commits, or GitHub release metadata.

Safety

Automatic checks are disabled by default, and automatic manifest changes are not supported. Manual and periodic discovery never approve new projects automatically. Newly found projects remain unavailable to monitoring, GitHub publishing, and Store-readiness workflows until the user selects and confirms maintained development copies in the approval window. Nothing is selected by default. Only projects containing Git metadata or recognized NVDA build files are eligible. Installed add-ons, packages, output folders, system folders, caches, translations, runtime tests, and cloud-only placeholders are ignored. Required manifest metadata is validated first. Every selected manifest receives a project-specific backup before it is changed.

Routine background checks inspect previously approved manifests directly. At the configured periodic recheck interval, project discovery also runs in the external worker across configured development and synchronized-cloud roots so newly created add-ons can be reported for approval. Discovery is cancellable, throttled, and bounded to 60 seconds or 20,000 directories per invocation. Full-drive discovery remains manual and opt-in.

The updater does not parse project source trees inside NVDA. When automatic checking is disabled, no updater monitor thread is created.

Release lookup runs on the updater thread with strict network timeouts, GitHub ETag caching, official release-feed fallback, and saved last-known-good fallback. Stable releases, release candidates, betas, and direct alpha snapshots use this one tested implementation. Recursive filesystem discovery remains in the separate, hidden, below-normal-priority PowerShell process. Routine unchanged background release checks do not launch that worker. Cancelling a scan terminates it.

Automatic checks wait after NVDA starts and use exponential backoff after repeated failures. Unchanged update and error announcements are suppressed. The first cached fallback, a new or changed action, validation recovery, and restored live service are announced. Manual checks always provide a full result. A new alpha build in the same compatibility family is explicitly reported as requiring no manifest change solely for that build.

Before a compatibility update, the review and confirmation identify each path, minimum and proposed NVDA versions, Git branch, and uncommitted manifest state. The official release is rechecked immediately before writing; a newer compatibility family defers the change. Updated manifests are revalidated, failed writes are rolled back, and the assignable update undo command refuses to overwrite later edits. Long-running operations display stage text. Manifest checking changes to determinate per-project progress, while work with unknowable duration uses a repeating activity percentage. NVDA's progress-bar settings control feedback.

Settings

Use NVDA Settings, Add-on Developer Updater to control automatic checks, prereleases, additional development roots, full-drive manual discovery, release intervals, and periodic rechecking of saved projects. The prerelease option is enabled by default and includes NVDA alpha snapshots, beta builds, and release candidates. Disable it only when you want scans to follow stable releases exclusively. Current alpha identifiers use a build format such as alpha-57626,71bae80b (2026.3.0.57626). The updater reads the official alpha snapshot listing and NVDA source version together, mapping that example to the 2026.3 compatibility family.

Privacy and network activity

  • Scans read folder names, manifests, and selected project files locally. Cloud folders are scanned through copies synchronized and accessible on this computer.
  • Background checks inspect approved projects and configured development roots. Full-drive discovery is manual and opt-in.
  • Release checks contact NV Access and the official NVDA GitHub repository.
  • GitHub commands use the account authenticated in GitHub CLI. Repository metadata, templates, commits, and packages are sent to GitHub only for a command the user confirms.
  • The Store-readiness check downloads release packages for local verification but never submits a form or stores a GitHub password or token.
  • Updater state, release cache, and backups remain in the active NVDA configuration folder.

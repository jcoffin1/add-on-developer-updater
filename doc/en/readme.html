Add-on Developer Updater

Version 2026.2.25. Add-on versions follow the current stable NVDA release family.

This add-on checks official NVDA releases and safely monitors approved NVDA add-on development projects in configured folders and locally synchronized cloud storage.

Commands

Press NVDA+Alt+Shift+U to start a manual check and save its results. No dialog opens automatically after a scan. A separate command named Review previously discovered NVDA add-on compatibility updates opens the saved review list when you choose. Commands for scanning all accessible drives and cancelling a running scan are also available under Add-on Developer Updater in NVDA's Input Gestures dialog and can be assigned custom gestures.

The review window is modeless: it does not block NVDA's main event loop, and NVDA commands continue to work while the window is open. In its update list, press Space to check or uncheck an item, Control+A to select all, Enter to update the checked items, or Escape to close.

Manifest updates are announced but no longer open project folders automatically.

Press NVDA+Alt+Shift+D to open the modeless compatibility downgrade window. Each entry states its current last-tested and minimum NVDA versions. Enter an older target such as 2026.2, select add-ons with Space, and choose Downgrade selected. Only lastTestedNVDAVersion changes; source code and the add-on's own version remain untouched. The target must be older than the current compatibility version and cannot be older than minimumNVDAVersion. Every changed manifest is backed up first. The focused results dialog names every unchanged add-on and its exact reason.

Press NVDA+Alt+G or NVDA+Alt+Shift+G to open an accessible checklist of approved development projects. Nothing is selected by default. Select the projects to inspect and publish with Space, use Control+A to select all, and press Enter to continue. The preflight then filters the selection to projects with changed files, unpushed commits, no GitHub remote, or a local version that differs from the newest GitHub Release. Changes can include Python code, manifests, documentation, translations, tests, or configuration. A modeless Yes/No confirmation reports changed-file and unpushed-commit counts and public repositories that will be created before anything is staged or pushed. Credential-like files cause the preflight to fail. During longer operations, NVDA announces each project's inspection, repository preparation, commit, push, package upload, and release completion, including its position in the selected list. After a successful source push, the add-on compares each local manifest version with the newest GitHub Release. Matching versions are skipped. Missing or different releases are listed with both versions in a separate Yes/No confirmation asking whether to publish the local versions. Git and GitHub commands run on worker threads and require an authenticated GitHub CLI installation.

When multiple local copies of one add-on exist, GitHub publishing shows only the copy with the newest add-on version. Numeric components are compared numerically, so version 1.10 is newer than 1.9. If versions match, the primary development folder is preferred.

A Codex work copy is hidden in favor of a primary development copy only when its add-on version is equal or older. A newer work copy remains eligible, ensuring its own GitHub remote and release history are inspected.

Repository discovery applies to every selected add-on. The updater uses the local origin remote first, then a GitHub repository URL in the manifest, then a matching repository in the signed-in GitHub account. It creates a new public repository only when none of those exists, and connects the local repository before pushing.

After GitHub inspection, NVDA announces each selected add-on's current GitHub Release and newest local version before asking whether to push anything. A repository with no release is announced as none. A new release targets the exact commit just pushed, even when the development branch differs from the repository's default branch.

During interactive GitHub operations, the updater progress window remains active and its focused status field is updated with every spoken publishing message. Focus moves from it only when the updater opens a confirmation or GitHub sign-in page, or when the operation finishes. Background scans remain non-activating.

If the newest local release is already published on GitHub, a focused information dialog says that the GitHub releases are current. Press OK to close it.

Existing GitHub Release assets are imported into the updater's submission metadata when their release version matches the newest local version. This allows the store-submission command to use releases created before the updater recorded them.

The store-submission gate verifies every add-on independently. Its release must use HTTPS on github.com, belong to the currently signed-in GitHub account, and contain a downloadable .nvda-addon asset from the same repository and matching release tag. The updater safely downloads the asset and verifies that its root manifest contains the expected add-on ID and local version; cosmetic package filenames may differ. The local working tree must have no changed files or unpushed commits. Ready and blocked add-ons are listed separately, with every blocked add-on's exact reasons. Only verified-ready forms can be opened.

Choosing No during GitHub sign-in, push, or release confirmation ends on a focused updater result dialog instead of returning directly to the previously active application.

When a progress window is replaced by a confirmation or result dialog, delayed progress cleanup restores focus to the replacement dialog. This prevents Windows from activating the application that was focused before publishing began.

If an add-on with the same manifest name exists both under the primary Documents\NVDA Add-on Development\Add-ons tree and a Documents\Codex work directory, the Codex work copy is persistently ignored. The GitHub command announces how many duplicate work copies were hidden, and visible projects are labeled by location. Same-name projects elsewhere are not removed automatically.

If GitHub CLI is not signed in from NVDA's process, the add-on offers a modeless Yes/No sign-in prompt with Yes focused by default. Pressing Enter starts GitHub's secure browser device flow, copies its one-time code to the clipboard, explicitly opens GitHub's device authorization page, and automatically retries the publishing preflight after authorization. The add-on never requests or stores a GitHub password or token.

Press NVDA+Alt+Shift+S to choose which approved add-ons to review for store submission. Nothing is selected by default. For each selected add-on, the updater checks the newest local copy, GitHub repository and exact-version release, the downloaded package manifest, current NVDA API-version requirements, HTTPS metadata, release channel, and every shipped text file for automated-authorship or generated-code disclosures. Legitimate references to a product the add-on supports, such as ChatGPT, are not treated as authorship disclosures. Any blocker is reported with the affected file and line when available, and no form is opened for that add-on. When all checks pass, the updater offers to open a prefilled official issue form for the user to review and submit personally. The updater never creates or comments on an addon-datastore issue; final review and submission are always performed by the user in the official form.

Store form titles and ready-list labels use each repository's current GitHub name. The manifest name remains the stable internal NVDA add-on ID used to verify package identity, so rebranding a repository does not break upgrades for existing users.

Only when preparing the official store form, the publisher field is filled as Justin Coffin. This does not rewrite an add-on manifest's author field, source files, Git commits, or GitHub release metadata.

Safety

Automatic checks are disabled by default, and automatic manifest changes are not supported. A manual scan approves the projects it finds and opens an accessible checklist of available compatibility changes. Nothing is selected by default. Only projects containing Git metadata or recognized NVDA build files are eligible. Installed add-ons, packages, output folders, system folders, caches, translations, runtime tests, and cloud-only placeholders are ignored. Required manifest metadata is validated first. Every selected manifest receives a project-specific backup before it is changed.

Routine background checks inspect previously approved manifests directly. At the configured periodic recheck interval, project discovery also runs in the external worker across configured development and synchronized-cloud roots so newly created add-ons can be reported for approval. Discovery is cancellable, throttled, and bounded to 60 seconds or 20,000 directories per invocation. Full-drive discovery remains manual and opt-in.

The updater does not parse project source trees inside NVDA. When automatic checking is disabled, no updater monitor thread is created.

Release lookup and all recursive filesystem discovery run in a separate, hidden, below-normal-priority PowerShell process. NVDA only launches the worker, waits without holding its interpreter, and reads the resulting manifest paths. Cancelling a scan terminates the external worker.

Completion notifications name projects with available or completed updates and announce their NVDA compatibility version changes. Announcements list up to five projects per category; complete results are written to the NVDA log and saved in the updater state file.

Long-running scans, manifest updates, compatibility downgrades, GitHub safety checks, sign-in, pushes, and release uploads display a standard modeless progress bar without taking focus. It advances by 10 percentage points every two seconds and repeats because the duration cannot be estimated. NVDA's own progress-bar settings control whether progress is reported with beeps, speech, both, or no feedback. The indicator closes on completion, cancellation, failure, or NVDA shutdown.

Settings

Use NVDA Settings, Add-on Developer Updater to control automatic checks, prereleases, opt-in automatic changes, additional development roots, full-drive manual discovery, release intervals, and periodic rechecking of saved projects. The prerelease option is enabled by default and includes NVDA alpha snapshots, beta builds, and release candidates. Disable it only when you want scans to follow stable releases exclusively. Current alpha identifiers use a build format such as alpha-57626,71bae80b (2026.3.0.57626). The updater reads the official alpha snapshot listing and NVDA source version together, mapping that example to the 2026.3 compatibility family.

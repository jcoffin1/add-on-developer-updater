Add-on Developer Updater

Version 2026.2.55. Add-on versions follow the current stable NVDA release family. This release supports NVDA 2025.3.3 and later and is tested through NVDA 2026.2.

This add-on checks official NVDA releases and safely monitors tracked NVDA add-on development projects in configured folders and locally synchronized cloud storage.

Quick start

  1. Press NVDA+Alt+Shift+U to scan your normal development folders.
  2. When the scan finds add-on projects, a window titled Choose add-ons to track opens. Check only the add-ons you are developing yourself. Leave others unchecked, such as someone else's add-on you downloaded, a backup, or a test copy. Check Hide the unchecked add-ons to stop the others from being offered after every scan. Copies of the same add-on are listed together, newest first. Each line gives the add-on's name and version, whether it is the newest copy, whether you already track another copy, whether its code is on GitHub with everything pushed, or only on this computer, its branch when it is not the main branch, when it last changed, and its folder.
  3. Assign the command named Review previously discovered NVDA add-on compatibility updates in NVDA's Input Gestures dialog.
  4. Run that command, select intended manifests with Space, and press Enter to review the exact changes.
  5. Review all changed source and documentation before using the GitHub publishing command.
  6. Press NVDA+Alt+Shift+S for the final Store-readiness check. Review and submit the official form yourself.

Commands

Press NVDA+Alt+Shift+U to start a manual check and save its results. If new add-on projects are found, the Choose add-ons to track window opens after the scan; nothing is checked until you check it. Separate assignable commands review saved compatibility updates, undo the most recent group of discovered compatibility updates, choose which found add-on projects to track, report complete update-check status, scan all accessible drives, and cancel a running scan, manifest operation, or GitHub operation. GitHub operations stop between projects; a push or upload already in progress is allowed to finish, and the result lists what was completed.

The review window is modeless: it does not block NVDA's main event loop, and NVDA commands continue to work while the window is open. In its update list, press Space to check or uncheck an item, Control+A to select all, Enter to update the checked items, or Escape to close.

Manifest updates are announced but no longer open project folders automatically.

Press NVDA+Alt+Shift+D to open the modeless Set an older NVDA compatibility target window. Official NVDA Add-on Store versions are loaded on a worker thread, with the last successful response saved for offline fallback. Select add-ons first; the version list then offers only older targets valid for every selected manifest and never offers a target below any selected minimumNVDAVersion. Experimental targets are offered only when every selected manifest uses the beta or development update channel. Each entry states the add-on path, Git branch, current last-tested and minimum NVDA versions, and whether the manifest has uncommitted changes. Review compatibility changes opens a final confirmation naming every proposed change and warning about dirty manifests. Only lastTestedNVDAVersion changes; NVDA, source code, minimumNVDAVersion, and the add-on's own version remain untouched. This metadata change does not prove code compatibility. If source uses newer NVDA APIs, check out the appropriate older source branch instead. Every changed manifest is backed up and revalidated. Failed validation restores the original automatically.

The command named Undo the most recent compatibility target changes is available in NVDA's Input Gestures dialog. It restores the last group of compatibility manifests only while each manifest is byte-for-byte unchanged since the operation. Missing backups, changed manifests, and invalid restored files are reported without overwriting later work.

Press NVDA+Alt+G or NVDA+Alt+Shift+G to open an accessible checklist of tracked development projects. Tracked manifests are loaded and de-duplicated on a worker thread before the checklist opens, so unavailable or synchronized paths do not block NVDA's main thread. The GitHub and Store commands retain separate selection windows. Nothing is selected by default. Select the projects to inspect and publish with Space, use Control+A to select all, and press Enter to continue. The preflight then filters the selection to projects with changed files, unpushed commits, no GitHub remote, or a local release that must be created or repaired. Changes can include Python code, manifests, documentation, translations, tests, or configuration. A modeless Yes/No confirmation reports changed-file and unpushed-commit counts and public repositories that will be created before anything is staged or pushed. Credential-like files cause the preflight to fail and are checked again immediately before staging. During longer operations, NVDA announces each project's inspection, repository preparation, commit, push, package upload, and release completion, including its position in the selected list. The add-on checks recent non-draft releases for the exact local version, not only the newest release. If that version already has a complete package from the current commit, it is not recreated. If its asset is missing or invalid, the updater can replace that asset only when the existing tag still identifies the current commit. When local changes are not contained in an already released version, the updater offers to increment the patch version, such as 2026.2.47 to 2026.2.48. With confirmation it changes the manifest version, any matching addon_version in buildVars.py, and readme lines that begin with the old version, then runs the publishing check again so every change is reviewed before anything is pushed. Choose No to skip those add-ons; versions that are not numeric still require a manual increment. GitHub Release notes come from the matching version section of the project's CHANGELOG.md, or from the manifest changelog when the project has no changelog file. Notes are never generated from commit messages; when no reviewed notes are available, a fixed one-line description is used. Project build.ps1 builders receive -Version only when they declare that parameter. The exact locally built package is validated before pushing and again before uploading. Validation includes parsing every packaged Python file with the grammar of the Python version bundled with the add-on's minimumNVDAVersion: Python 3.7 for NVDA 2019.3 to 2023.3, Python 3.11 for NVDA 2024.1 to 2025.3, and Python 3.13 for NVDA 2026.1 and later. Code that the oldest supported NVDA could not load stops publishing before anything is pushed. If no usable changelog notes exist for a new release, the publishing confirmation says so before any changes are made. Git and GitHub commands run on worker threads and require an authenticated GitHub CLI installation.

Press NVDA+Alt+Shift+F to load the newest released .nvda-addon files owned by the GitHub account currently signed in through GitHub CLI. The network lookup runs on a worker thread. For each repository, the newest non-draft release containing an add-on package is presented in an accessible single-selection list with its release tag, asset filename, and public, private, archived, or prerelease status. Repositories without a downloadable add-on package are excluded. Choose Copy download link or press Enter to place the selected asset's direct HTTPS download link on the clipboard. Choose Copy repository link, immediately below it, to copy the selected repository's GitHub page. The gesture can be changed in NVDA's Input Gestures dialog.

Press NVDA+Alt+Shift+I to select an owned NVDA add-on repository and open its GitHub Issues page. Repositories where Issues are disabled are identified and are not opened.

Press NVDA+Alt+Shift+T to select an owned NVDA add-on repository and choose an existing Markdown or YAML file directly inside .github/ISSUE_TEMPLATE. The accessible Form tab provides clearly explained template fields and, for GitHub YAML issue forms, a question list with controls for each question's type, ID, label, help text, placeholder, rendered language, default value, options, and required state. Every editable control has an explicit accessibility name, ensuring NVDA announces its purpose when focus moves to it. Every label explains where its value appears or what it changes on GitHub. Technical YAML types are spoken as Short answer, Long answer, Drop-down choice list, Checkbox list, and Information text. The editor defines Markdown as ordinary text with optional formatting symbols, gives examples for headings, bullets, and links, and makes clear that ordinary unformatted text is acceptable. Questions can be added, removed, or reordered before saving. A Raw Text tab supports advanced edits and files such as config.yml. Switching from raw text back to the form validates the YAML first. Form editing preserves unrecognized properties but may normalize YAML formatting and comments. Control+S or Save to GitHub opens a confirmation before any change is made. Delete Template has a separate warning and confirmation. Saving and deleting include the exact file revision that was loaded, so GitHub rejects a conflicting operation rather than overwriting or removing a newer remote edit. The editor also rejects invalid required metadata, duplicate or malformed question IDs, empty choices, empty files, files larger than 1 MB, nested paths, unsupported extensions, incomplete repository trees, and archived repositories.

When multiple local copies of one add-on exist, GitHub publishing shows only the copy with the newest add-on version. Numeric components are compared numerically, so version 1.10 is newer than 1.9. If versions match, the primary development folder is preferred.

A Codex work copy is hidden in favor of a primary development copy only when its add-on version is equal or older. A newer work copy remains eligible, ensuring its own GitHub remote and release history are inspected.

Repository discovery applies to every selected add-on. The updater uses the local origin remote first, then a GitHub repository URL in the manifest, then a matching repository in the signed-in GitHub account. It creates a new public repository only when none of those exists, and connects the local repository before pushing.

After GitHub inspection, NVDA announces each selected add-on's current GitHub Release and newest local version before asking whether to push anything. A repository with no release is announced as none. A new release targets the exact commit just pushed, after verifying that the commit is contained in the repository's default branch.

Before publishing, the updater announces each selected project's working branch and GitHub default branch. Before creating a tag or GitHub Release, it fetches the current default branch and verifies that the exact pushed commit is contained there. If a development commit is not there yet but the remote default branch has no competing commits, a separate Yes/No confirmation offers to push the exact commit to the named default branch, reverify it, and continue to release confirmation. This does not check out, merge, or move the developer's local branches. The updater never combines diverged histories and does not bypass GitHub branch protection. If a safe update is unavailable or rejected, it offers to open GitHub's comparison page so the developer can review and merge a pull request, then run publishing again. A detached Git HEAD or a working-branch change after the publishing review stops the operation.

During interactive GitHub operations, the updater progress window remains active and its focused status field updates both its text value and accessibility name with every spoken publishing message, keeping speech and braille synchronized. GitHub selections, progress, confirmations, errors, and completion messages use the public add-on summary while the internal manifest name remains reserved for package verification. Focus moves from the progress window only when the updater opens a confirmation or GitHub sign-in page, or when the operation finishes. Background scans remain non-activating.

If the newest local release is already published on GitHub, a focused information dialog says that the GitHub releases are current. Press OK to close it.

Existing GitHub Release assets are imported into the updater's submission metadata when their release version matches the newest local version. This allows the store-submission command to use releases created before the updater recorded them.

The store-submission gate verifies every add-on independently. Its release must use HTTPS on github.com, belong to the currently signed-in GitHub account, and contain a downloadable .nvda-addon asset from the same repository and matching release tag. The updater safely downloads the asset and verifies that its root manifest contains the expected add-on ID and local version; cosmetic package filenames may differ. The local working tree must have no changed files or unpushed commits. Ready and blocked add-ons are listed separately, with every blocked add-on's exact reasons. Only verified-ready forms can be opened.

Choosing No during GitHub sign-in, push, or release confirmation ends on a focused updater result dialog instead of returning directly to the previously active application.

When a progress window is replaced by a confirmation or result dialog, delayed progress cleanup restores focus to the replacement dialog. This prevents Windows from activating the application that was focused before publishing began.

If an add-on with the same manifest name exists both under the primary Documents\NVDA Add-on Development\Add-ons tree and a Documents\Codex work directory, an equal or older Codex work copy is hidden. A newer work copy remains available. The GitHub command announces how many duplicate work copies were hidden, and visible projects are labeled by location. Same-name projects elsewhere are not removed automatically.

GitHub features do not require sign-in during add-on installation or NVDA startup. When a publishing, link-copying, Issues, template, or store-readiness command is used, the add-on first checks for GitHub CLI and an authenticated account. If GitHub CLI is missing or cannot be found, an accessible Yes/No prompt with Yes focused offers to open its official installation page. Installation is never automatic; restart NVDA and run the command again after installing it. If GitHub CLI is not signed in from NVDA's process, the add-on offers a modeless Yes/No sign-in prompt with Yes focused by default. Pressing Enter starts GitHub's secure browser device flow, copies its one-time code to the clipboard, explicitly opens GitHub's device authorization page, and automatically retries the requested operation after authorization. The add-on never requests or stores a GitHub password or token.

Press NVDA+Alt+Shift+S to choose which tracked add-ons to review for store submission. Nothing is selected by default. For each selected add-on, the updater checks the newest local copy, GitHub repository and exact-version release, the downloaded package manifest, current NVDA API-version requirements, HTTPS metadata, release channel, and every shipped text file for automated-authorship or generated-code disclosures. Legitimate references to a product the add-on supports, such as ChatGPT, are not treated as authorship disclosures. Any blocker is reported with the affected file and line when available, and no form is opened for that add-on. When all checks pass, the updater offers to open a prefilled official issue form for the user to review and submit personally. The updater never creates or comments on an addon-datastore issue; final review and submission are always performed by the user in the official form.

Store form titles and ready-list labels use each repository's current GitHub name. The manifest name remains the stable internal NVDA add-on ID used to verify package identity, so rebranding a repository does not break upgrades for existing users.

Only when preparing the official store form, the publisher field is filled from the manifest author without e-mail addresses, or from the Add-on Store publisher setting when it is set. The license fields are filled from a recognized GPL, LGPL, MIT, Apache, or Mozilla license file in the project, or from the fallback license settings; otherwise they are left blank for you to complete. This does not rewrite an add-on manifest's author field, source files, Git commits, or GitHub release metadata.

Managing tracked add-ons

Press NVDA+Alt+Shift+A to open Manage tracked add-ons. It lists every add-on copy found on your computer, and each line begins with your current choice: Tracked, Not tracked, or Hidden. Select a copy and press T to track it, N to stop tracking it, or H to hide it, or use the choice below the list. Tracked add-ons are checked for new NVDA versions and can be published to GitHub and the Add-on Store. Not tracked add-ons are offered again after each scan. Hidden add-ons are not offered again until you change them here. Press Enter or Save changes, then confirm. Stopping tracking also withdraws any pending NVDA update for that copy. The window gathers fresh Git details when it opens, so each line correctly says whether the copy is on GitHub, has uncommitted files or unpushed commits, or is only on this computer.

The update review window names each add-on with its version and marks older copies. It also says whether the Add-on Store accepts the target NVDA version on the stable channel, with the date of that information, and reminds you to test with a beta or release-candidate NVDA build before publishing.

Speech and braille

Every question and result opens in a window whose message is a read-only text field, and the field has focus when the window opens. NVDA speaks the first line, which always states the question or the outcome, such as "Publish 2 add-ons to GitHub?" or "Scan complete: 1 update available, 3 projects current." Each further fact is on its own line, so you can read the details with the Up and Down Arrow keys or line by line on a braille display. Press Tab to reach the buttons.

In a question window, Escape always answers No. Enter in the message chooses the highlighted button, which is No unless the action is harmless, such as signing in. In a result window, Escape or Enter closes it. Results are no longer spoken separately before their window opens, so nothing is heard twice. If a new result arrives while a result window is open, it appears at the top and the earlier result stays below it.

The progress window shows the current step in a text field that speech and braille both follow. Its progress bar appears only when the number of steps is known, so NVDA never beeps or speaks a percentage that does not measure real progress. When an automatic check in the background finds something new, a short tone plays before the announcement; turn this off in settings.

Safety

Automatic checks are disabled by default, and automatic manifest changes are not supported. Scans never start tracking an add-on on their own. A newly found add-on is not checked for NVDA updates, published to GitHub, or offered for the Add-on Store until you check it in the Choose add-ons to track window and confirm. Nothing is selected by default. Only projects containing Git metadata or recognized NVDA build files are eligible. Installed add-ons, packages, output folders, system folders, caches, translations, runtime tests, and cloud-only placeholders are ignored. Required manifest metadata is validated first. Every selected manifest receives a project-specific backup before it is changed.

Routine background checks inspect previously tracked manifests directly. Manual and periodic discovery scan the standard NVDA development folder, an existing Documents\Codex workspace, configured development folders, and synchronized-cloud roots for new projects. They also merge every existing tracked manifest path into the result, including maintained repositories outside those roots. Discovery is cancellable, throttled, and bounded to 60 seconds or 20,000 directories per invocation, with a 90-second hard process limit in case Windows blocks inside a filesystem call. It searches level by level, so shallow project folders everywhere are checked before any large test or dependency tree, and Git and editor metadata folders are skipped. When the limit is reached, the result states how many folder levels were searched completely. An tracked manifest that becomes missing or cloud-only is reported as unavailable in every scan mode instead of retaining an obsolete saved update status. Full-drive discovery remains manual and opt-in.

The updater does not parse project source trees inside NVDA. When automatic checking is disabled, no updater monitor thread is created.

Release lookup runs on the updater thread with strict network timeouts, using the live GitHub API first, the official NVDA releases feed second, and saved last-known-good information only after both live sources fail. When prereleases are enabled, a manual scan first opens an accessible build chooser containing the newest meaningful stable, beta, release candidate, and alpha choices. Stable is selected initially, and the last successful manual choice is remembered while available. Each row states the channel, exact build, manifest compatibility target, and information source. For example, alpha-57626,71bae80b (2026.3.0.57626) is shown separately from its 2026.3 manifest target. The exact choice and pending results are stored separately from background-check state, so an automatic check cannot replace them before review. Unselected items remain pending after selected manifests are updated. The exact choice is revalidated before writing and is never silently replaced by another channel. Scans propose only newer targets; use the separate compatibility-target command to set an existing manifest to an older target. Recursive filesystem discovery remains in the separate, hidden, below-normal-priority PowerShell process. Routine unchanged background release checks do not launch that worker. Cancelling a scan terminates it.

Automatic checks wait after NVDA starts and use exponential backoff after repeated failures. Unchanged update and error announcements are suppressed. The first cached fallback, a new or changed action, validation recovery, and restored live service are announced. Manual checks always provide a full result. A new alpha build in the same compatibility family is explicitly reported as requiring no manifest change solely for that build.

Before a compatibility update, the review and confirmation identify the selected exact NVDA build, its manifest compatibility target, each path, minimum and proposed NVDA versions, Git branch, and uncommitted manifest state. The exact selected release is rechecked immediately before writing; an unavailable selection defers the change for a fresh scan. Updated manifests are revalidated, failed writes are rolled back, and the assignable update undo command refuses to overwrite later edits. Run another manual scan with another target to update a different group. Long-running operations display stage text. Manifest checking changes to determinate per-project progress, while work with unknowable duration uses a repeating activity percentage. NVDA's progress-bar settings control feedback. Closing the progress window leaves the operation running safely in the background and does not leave a destroyed progress control for later updates.

Settings

Use NVDA Settings, Add-on Developer Updater to control automatic checks, prereleases, additional development roots, full-drive manual discovery, release intervals, periodic rechecking of saved projects, the Add-on Store publisher name, and a fallback license name and address for projects without a recognized license file, and whether a tone plays when an automatic check finds something new. The prerelease option is enabled by default and makes NVDA alpha snapshots, beta builds, and release candidates available in the manual scan chooser; it does not automatically select them. Disable it when only the current stable release should be available. Current alpha identifiers use a build format such as alpha-57626,71bae80b (2026.3.0.57626). The updater reads the official alpha snapshot listing and NVDA source version together, mapping that example to the 2026.3 compatibility family.

Privacy and network activity

  • Scans read folder names, manifests, and selected project files locally. Cloud folders are scanned through copies synchronized and accessible on this computer.
  • Background checks inspect tracked projects directly. Manual and periodic discovery inspect the standard NVDA development folder, an existing Documents\Codex workspace, synchronized cloud roots, and additional configured development roots. Full-drive discovery is manual and opt-in.
  • Release checks contact NV Access and the official NVDA GitHub repository.
  • GitHub commands use the account authenticated in GitHub CLI. Repository metadata, templates, commits, and packages are sent to GitHub only for a command the user confirms.
  • The Store-readiness check downloads release packages for local verification but never submits a form or stores a GitHub password or token.
  • Updater state, release cache, and backups remain in the active NVDA configuration folder.
